The State Oracle records assertion policy. The Credible Registry records authorized builders and credible blocks. Guards check the Registry before protected operations execute.

Registering an assertion does not install a guard or configure transaction routing. See [Ethereum Architecture](./architecture-overview) for the complete execution path.

## Components

| Component | Responsibility |
| --- | --- |
| State Oracle | Assertion assignments, manager authority, and lifecycle timing. |
| Admin verifier | Authorization checks when registering an assertion adopter. |
| DA verifier | Verification of the artifact availability proof used for registration. |
| Credible Registry | Builder authorization and credible-block markers. |
| Credible Block Guard | Restriction on protocol operations that invoke the guard. |
| Credible Safe Guard | Restriction on Safe owner-authorized transactions through the supported transaction-guard path. |

### State Oracle

The State Oracle associates protected contract addresses, called assertion adopters, with a Protocol Manager and assertion activation windows. Its configured block delay governs additions and removals. The enforcer reads this state to determine applicable assertions.

In the [public State Oracle implementation](https://github.com/phylaxsystems/credible-layer-contracts/blob/main/src/StateOracle.sol), an assertion ID cannot be re-added for the same adopter after removal. Confirm the deployed implementation and configuration when planning updates.

### Protocol Admin Verification

An approved verifier establishes authority during registration. Supported paths depend on the deployment and can include ownership interfaces or an initial-manager interface. Platform membership alone does not grant on-chain manager authority. See [Managing Policy Deployments](./managing-policy-deployments).

### Data Availability Verification

The lifecycle verifies an artifact availability proof before accepting an assertion. The ECDSA verifier uses a signature from the Assertion DA prover. This binds registration to available creation data; it does not prove that a builder subsequently executed the assertion. See [Assertion DA](./assertion-da).

### State Oracle Administration

The public implementation separates governance, operator, and guardian permissions. These control verifier configuration, registration allowlisting, and manager revocation or assertion removal. Guardian removal uses the configured removal delay; it is not an immediate universal off switch.

Review the deployed roles and timing alongside the [Trust Model](./trust-model). These permissions are separate from Credible Registry administration.

### Credible Registry

The Registry authorizes builder addresses and records whether a block has been marked credible. An authorized builder calls `markCurrentBlockCredible` with the expected block timestamp before protected operations execute. Guards can query `isCredibleBlock` and `lastCredibleBlock`.

The marker attests that the builder followed the validation policy. The Registry does not execute assertions or verify a cryptographic proof of their execution. Builder behavior, marker publication, and Registry administration remain trust assumptions.

Builder authorization changes follow the Registry's own governance and timing rules. They are independent of a protocol's assertion-manager permissions and State Oracle lifecycle.

### Credible Block Guard

Protocol code invokes the guard on each protected execution path. While the gate is active, an unmarked block causes the protected operation to revert. The guard can permit configured bypass accounts, and its block-gap fallback activates when the latest credible block is **strictly more** than the configured threshold behind.

An included guard revert consumes transaction gas. A builder excluding a transaction before inclusion does not. Paths that never reach the guard remain outside its protection.

The reference guard propagates Registry read failures. Review the deployed implementation and any overrides rather than assuming all guards fail open on a Registry error.

### Credible Safe Guard

The Safe transaction guard checks owner-authorized `execTransaction` execution. Safe module paths require separate controls or an unavoidable downstream gate. Installing a transaction guard alone does not cover those modules.

The reference Safe guard also has a block-gap fallback. Unlike the generic guard, it fails open when Registry reads revert, return malformed data, or target an address without code. Its Registry and threshold configuration are immutable; changing them requires replacing the guard.

Both guards can relax the credible-block requirement during fallback. Participating builders can continue enforcing assertions, but operations submitted through other builders may then execute without those checks. Ordinary protocol authorization still applies.
