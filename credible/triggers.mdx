Triggers select when assertion functions execute. Match the trigger to the state or operation that the policy checks.

## Why Use Triggers?

Scoped triggers reduce execution cost. Choose a trigger that covers every path that can violate the policy.

## Trigger Behavior in Production

Each matching assertion executes independently. A participating builder excludes a candidate if any active production assertion fails.

## Trigger Types

### Function Call Triggers

Use `registerFnCallTrigger` when an assertion should run once for each successful call to a specific function. This is the preferred trigger for call-scoped checks because the assertion can read `ph.context()` and construct `PhEvm.ForkId({forkType: 2, callIndex: ctx.callStart})` / `PhEvm.ForkId({forkType: 3, callIndex: ctx.callEnd})` snapshots for the matched call.

**Example:**
```solidity
function triggers() external view override {
    registerFnCallTrigger(this.assertionOwnershipChange.selector, Ownable.transferOwnership.selector);
}
```

### Transaction End Triggers

Use `registerTxEndTrigger` when an assertion should run after any transaction that touches the protected contract. This is the preferred trigger for transaction-wide invariants where the relevant mutation can happen through multiple functions or indirect calls.

**Example:**
```solidity
function triggers() external view override {
    registerTxEndTrigger(this.assertAccountingInvariant.selector);
}
```

### State and Flow Triggers

Choose a narrower trigger when it still covers every mutation that matters:

| Policy | Trigger | Example |
| --- | --- | --- |
| Configuration must remain approved | `registerStorageChangeTrigger`, optionally restricted to a slot | [Safe configuration](https://github.com/phylaxsystems/credible-std/blob/fe49de6dcddb8ea1f77ea2828a0c9d7d5f923db0/src/protection/safe/SafeConfigLockAssertion.sol) |
| Check accounting when an ERC20 balance changes | `registerErc20ChangeTrigger` | [Vault policies](../assertions-book/assertions/vault-policies) |
| Bound net token flow over a rolling window | `watchCumulativeOutflow` or `watchCumulativeInflow` | [Cumulative flow](../assertions-book/assertions/ass20-erc20-drain) |
| Run a damage check when activity is unusual | `watchAnomaly` | [Anomaly policies and runtime limits](../assertions-book/assertions/anomaly-gated-policies) |

Storage triggers remain supported in current patterns. Use `registerFnCallTrigger` instead of legacy `registerCallTrigger` for new call-scoped policies. See the [library reference](./credible-std-overview#assertion-helpers) for helper signatures and specification requirements.

## Best Practices

Test that the trigger covers all relevant state changes, including indirect calls and alternative entry points. Narrow it only when those tests still pass.
