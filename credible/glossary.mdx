## Core Concepts

### The Credible Layer
Security infrastructure for protocol-defined assertions checked before block inclusion. Enforcement uses covered rollup sequencing paths or participating builders with application guards. See [Introduction](./credible-introduction).

### Assertion
A smart contract that verifies specific properties or behaviors of other smart contracts. Assertions are the fundamental building blocks of the Credible Layer, used to enforce security properties and invariants.

Learn more: [What are Assertions?](/credible/assertions-overview) | [Assertion Guide](/credible/write-first-assertion)

### Protocol Invariants
Critical conditions or properties that must always be maintained within a protocol, such as ensuring total assets ≥ total liabilities or maintaining specific ownership rules. These invariants can be:
- Single-contract: Rules within a single contract
- Protocol-wide: Rules spanning multiple contracts and complex interactions
- Security-specific: Rules focused on preventing unauthorized access or changes

## System Architecture

### PhEVM (Phylax EVM)
A specialized EVM implementation that includes additional capabilities for assertion verification and state manipulation.

Learn more: [PhEVM](/credible/phevm)

### Assertion DA (Data Availability)
The data availability layer responsible for storing assertion code and metadata. This ensures that assertions are accessible and verifiable by anyone.

Learn more: [Assertion Data Availability](/credible/assertion-da)

### State Oracle
The core on-chain contract that coordinates protocol admins and network operators. It maintains the mapping between protected contracts and their assertions, enforces timelock periods, and manages assertion windows.

Learn more: [Credible Layer Contracts](/credible/credible-layer-contracts)

### Block Builder
A component that selects and orders transactions into candidate blocks. A participating builder evaluates applicable assertions and applies their verdicts before inclusion; other builders are not automatically subject to that policy.

### Sequencer
A rollup component responsible for transaction ordering and production. An integrated sequencer applies assertion verdicts on its covered transaction paths; sequencing alone does not imply assertion enforcement.

### Assertion Enforcer
The evaluator that selects applicable assertions and reports results to the integrated sequencer or builder. It can run as a sidecar or embedded component; the transaction builder retains inclusion authority. See [Assertion Enforcer](./assertion-enforcer).

### Platform
The [Phylax platform](https://app.phylax.systems) is the web application interface for interacting with the Credible Layer. It allows protocol teams and end-users to deploy, manage, and view assertions and projects.

### The Phylax Explorer
A public dashboard that displays the security and operational risk posture of protocols that have opted into runtime enforcement. It can show summaries of actions protected by circuit breakers and assertions, scenarios the assertions prevent, assertion and circuit breaker behavior, admin multisig details, contract upgradeability documentation, and deployed-vs-audited code context where available. Detailed project management data, staging invalidations, transaction payloads, and traces are only available in private project views.

### Sidecar
A component deployed alongside another process. Some rollup integrations run assertion evaluation this way. Sidecar versus embedded library is an implementation choice, separate from the [enforcement design](./credible-layer-overview).

### Network Validator (Node)
A node that checks network validity rules. Builder or sequencer assertion filtering is not automatically a consensus validity rule or a rollup-proof requirement.

### Credible Registry
The Ethereum contract that records authorized block markers and manages builder authorization. It is separate from the State Oracle assertion-policy registry. See [Registry Reference](./ethereum-guard-reference).

### Credible Block Guard
An application check restricting selected calls to marked blocks while its requirement is active, subject to its implemented fail-open and bypass rules.

### Marker Transaction
A transaction from an authorized marker caller that writes the current block into the Credible Registry before guarded calls in the same block. It is not cryptographic proof of correct assertion evaluation.

### Credible RPC
The supported simulation and private signed-submission interface for the Ethereum integration. It does not replace the guard or builder-side evaluation.

### Protected Target and Protected Function
A protected target is a contract whose behavior an assertion is intended to constrain. A protected function is an entry point covered by a guard or the integration’s enforcement path. Alternate unguarded paths and bypasses can limit coverage even when assertions are registered.

## Assertion Components

### Trigger
A function that determines when an assertion should be executed. Triggers are registered with the PCL system to specify the conditions under which an assertion should be evaluated. There are several types of triggers:
- Call Triggers: Execute on specific contract calls
- Storage Triggers: Execute on storage changes
- Balance Triggers: Execute on ETH balance changes

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for detailed information about different trigger types.

### Pre-state/Post-state
State immediately before and after the candidate transaction at its proposed execution position. Pre-state is not necessarily arrival-time state; post-state is not automatically end-of-block state or finality. See [Cheatcodes Reference](./cheatcodes-reference) for transaction and call-frame snapshots.

### State Changes
Modifications to contract storage that occur during transaction execution. These can be tracked and verified using the Credible Layer's state change tracking capabilities, allowing assertions to monitor and prevent unauthorized modifications.

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for state tracking functions.

### Callstack
The sequence of function calls that occur during a transaction's execution. PCL's ability to inspect state changes across the entire callstack is a powerful feature that enables assertions to:
- Track state modifications through complex contract interactions
- Monitor cross-contract dependencies
- Detect unauthorized changes in deeply nested calls
- Enforce invariants that span multiple contract boundaries

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for callstack inspection capabilities.

### Assertion Bytecode
The compiled form of an assertion contract that is stored in the Assertion DA and executed by the PCL network.

See the [pcl Reference](/credible/cli-reference) for build and store commands.

### Assertion ID
The Keccak256 hash of creation bytecode concatenated with encoded constructor arguments. It identifies deployable assertion data. See [Assertion DA](./assertion-da#assertion-id).

### Assertion DA Prover Signature
A signature checked during registration that attests to assertion-data availability when issued. It does not guarantee future retrieval or a ready evaluator. See [Assertion DA](./assertion-da).

### Assertion Adopter
The contract address associated with an assertion in the policy registry. With a hook/adapter integration, the adapter can be the adopter while the assertion inspects a different protected target.

### Assertion Group
A collection of assertions in the same contract that are related to the same protocol contract. This allows for organizing multiple assertions that protect different aspects of the same protocol.

### Assertion Function
A function in an assertion contract that performs a specific check. These functions must be registered in the `triggers()` function and are called by the PCL system when their trigger conditions are met.

## Development Tools

### `pcl`
The command-line tool for building, testing, and deploying assertions to the Credible Layer.

See the [pcl Reference](/credible/cli-reference) for all available commands.

### `phorge`
A minimal fork of Forge with functionality for assertion execution, used for testing and running assertions in the Credible Layer. It provides the infrastructure needed to compile, test, and deploy assertions.

### `credible-std`
The Phylax smart contract library that provides the base contracts and utilities for writing assertions. It includes the interfaces and implementations needed to interact with the Credible Layer's cheatcodes and assertion system.

### Cheatcodes
Special precompiles (similar to Ethereum's native precompiles) that provide additional capabilities for state manipulation, forking, and assertion management in the PhEVM environment. These are accessed through the credible-std library.

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for a complete list of available cheatcodes and their usage.

### Test Environment
The PCL testing interface that extends Forge's testing capabilities with additional utilities specifically for testing assertions. It provides functions for adding assertions and validating transactions, making it easier to test assertion behavior in different scenarios.

Learn more about testing assertions in the [Testing Guide](/credible/testing-assertions).

### Backtesting
An automatic platform release check that tests every assertion in a release against transactions from the last 20,000 blocks. The result identifies historical transactions that the release would have invalidated so you can review false positives before deployment.

Learn more: [Backtesting](/credible/backtesting)

## Security Features

### Off-chain Execution
The ability to run complex security rules outside the main blockchain execution, providing significant efficiency gains compared to on-chain validation.

### Forced Inclusion Transactions
Special transactions that may have protocol-level inclusion guarantees, such as L1->L2 deposits. Network integrations define the validation policy for these transaction paths.

### Circuit Breaker
An assertion pattern that collects value flowing into or out of a protected contract into one bucket per block, then limits the cumulative flow across those per-block buckets over a rolling window. Circuit breakers are useful when the goal is to reduce exploit velocity or contain blast radius rather than block one specific function call.

### Verifiability
The ability to inspect the rules and registry state behind a protocol's Credible Layer posture. Assertion IDs and registry entries are on-chain, while assertion bytecode is stored in Assertion DA. Public views expose the protocol's visible assertion posture; private project data remains restricted to authorized project users.

## Prevention

### Invalidation
A recorded assertion violation. It may reflect an exploit attempt, a false positive, or a policy bug. Exclusion and reporting depend on integration and environment; staging records observations without enforcement. See [Invalidations](./dapp-invalidations).

### Revert
An EVM execution failure that rolls back the affected call’s state. An off-chain assertion revert signals a failed rule. An application guard revert is a separate on-chain outcome; the transaction can still be included and consume gas.

### Drop
Exclusion of a candidate by a sequencer or builder. Dropping a transaction from one builder does not stop another builder including it. It is distinct from an included transaction reverting.

### Prevent
Exclude behavior that violates applicable assertions on enforced paths, or prevent a selected action through an active application guard. Coverage depends on the rule, integration, and documented exceptions.

## Assertion Lifecycle

### Apply
The process of creating a release on the platform using `pcl apply`. This command reads your `credible.toml` configuration, compiles assertion contracts, and creates a release. The platform handles storing assertion bytecode in [Assertion DA](/credible/glossary#assertion-da-data-availability) automatically.

Learn more: [Apply Assertions](/credible/apply-assertions) | [pcl Reference](/credible/cli-reference#apply)

### Deployment
The process of reviewing an assertion, linking it to a contract, and signing the transaction to deploy it on-chain. Deployment includes choosing whether to deploy to Staging or Production environment. The deployment transaction must succeed for the assertion to be deployed on-chain.

### Staging
A mirrored chain environment used for testing assertions without affecting production. Assertions run on staging to observe behavior, but transactions are not dropped if they break assertion rules. This allows protocol teams to test assertions safely before deploying to production.

### Production
The environment in which active assertions affect inclusion on enforced paths. The label alone does not establish backend support, guard coverage, or deployed readiness.

### Timelock
A period enforced by the on-chain State Oracle contracts between an assertion change and when that change takes effect. The timelock applies when you add an assertion and when you remove one. It exists for two reasons: (1) to provide latency for the enforcer to index on-chain state and prepare for enforcement changes, and (2) to give users time to expect changes to protocol behavior. During the timelock period, newly added assertions are marked for enforcement or staging but are not yet active, and removed assertions remain active until the timelock finishes.

### Marked for Enforcement
The state of an assertion deployed to production during the timelock period. The assertion is deployed but not yet actively preventing hacks. After the timelock expires, the assertion becomes enforced.

### Marked for Staging
The state of an assertion deployed to staging during the timelock period. The assertion is deployed but not yet running on the staging environment. After the timelock expires, the assertion becomes staged.

### Enforced
An active production policy applied on the integration’s enforced paths. Evaluation requires available code and a supported backend; it does not guarantee that every possible action is covered.

### Staged
The state of an assertion in staging after the timelock period has expired. A staged assertion is running on the mirrored chain environment, allowing protocol teams to observe how it behaves without transactions being dropped if they violate the assertion.

### Removal
The process of removing an assertion from active enforcement or staging. Removal is scheduled through the State Oracle contracts and requires the configured timelock to expire before the assertion stops being enforced or staged.
