Definitions of Credible Layer components, policy states, and platform terms.

## Core Concepts

### The Credible Layer
Ethereum security infrastructure combining protocol-authored assertions, participating builders, credible-block markers, and on-chain guards. Builders exclude candidates that fail active rules; guards restrict protected operations while their gate is active.

See the [Overview](./credible-introduction).

### Assertion
A smart contract that verifies specific properties or behaviors of other smart contracts. Assertions are the fundamental building blocks of the Credible Layer, used to enforce security properties and invariants.

Learn more: [What are Assertions?](/credible/assertions-overview) | [Writing Your Own Policies](./writing-your-own-policies)

### Protocol Invariants
Critical conditions or properties that must always be maintained within a protocol, such as ensuring total assets ≥ total liabilities or maintaining specific ownership rules. These invariants can be:
- Single-contract: Rules within a single contract
- Protocol-wide: Rules spanning multiple contracts and complex interactions
- Security-specific: Rules focused on preventing unauthorized access or changes

## System Architecture

### PhEVM (Phylax EVM)
A specialized EVM implementation that includes additional capabilities for assertion verification and state manipulation.

Learn more: [PhEVM](/credible/phevm)

### Assertion DA (Data Availability)
The data availability layer responsible for storing assertion code and metadata. This ensures that assertions are accessible and verifiable by anyone.

Learn more: [Assertion Data Availability](/credible/assertion-da)

### State Oracle
The core on-chain contract that coordinates protocol admins and network operators. It maintains the mapping between protected contracts and their assertions, enforces timelock periods, and manages assertion windows.

Learn more: [Credible Layer Contracts](/credible/credible-layer-contracts)

### Credible Registry
The on-chain contract that authorizes participating builders and records credible-block markers. It is separate from the State Oracle's assertion assignments and lifecycle state.

### Credible Block
A block marked credible by an authorized builder before protected operations execute. The marker is a builder attestation, not a cryptographic proof that assertions passed.

### Guard
An on-chain check restricting protected operations to credible blocks while its gate is active. Coverage and failure behavior depend on the implementation. A Safe transaction guard does not automatically cover Safe modules.

### Credible RPC
The transaction submission route to participating builders. Routing is separate from guard enforcement and does not itself guarantee inclusion or assertion success.

### Fail-open
A condition that relaxes a guard's requirement for a credible block to preserve availability. Transactions may then execute without mandatory assertion validation, while existing protocol checks remain active. Participating builders can continue enforcing assertions.

### Protocol Manager
The address authorized to manage assertion lifecycle for registered contracts through the State Oracle. This authority is distinct from platform membership, transaction submission, and protocol upgrade permissions.

### Block Builder
A component that selects and orders candidate transactions into blocks. A participating Credible Layer builder invokes the Assertion Enforcer before including transactions; other builders need not run assertions.

### Sequencer
An L2 component responsible for ordering transactions. See [L2 and Sequencer Integrations](./l2-integrations/overview) for its separate assertion-enforcement model.

### Assertion Enforcer
The sidecar component responsible for validating transactions against assertions during block production. It orchestrates the validation process by identifying relevant assertions, invoking PhEVM to execute them, and returning a validation report. The network integration applies the inclusion policy.

Learn more: [Assertion Enforcer](/credible/assertion-enforcer)

### Platform
The [Phylax platform](https://ethereum.phylax.systems) is the web application interface for interacting with the Credible Layer. It allows protocol teams and end-users to deploy, manage, and view assertions and projects.

### The Phylax Explorer
A public view of a small selection of featured projects. Where available, project pages show protected contracts, circuit-breaker summaries, operational authority, and supporting evidence. Detailed project information and transaction replays remain subject to access permissions.

### Sidecar
A software architecture pattern where a component runs alongside the main application without changing core protocol rules. The Credible Layer operates as a sidecar to the network's block builder, intercepting and validating transactions during the block building process.

See [Architecture](./architecture-overview#how-the-credible-layer-works) for implementation details.

### Network Validator (Node)
An Ethereum validator participates in consensus and may propose a block assembled by a builder. Validators apply Ethereum's consensus rules; they do not independently run Phylax assertions as part of block validity. A participating [block builder](#block-builder) runs the assertion integration before publishing its candidate.

For the different roles in an L2 sequencer architecture, see [L2 and Sequencer Integrations](./l2-integrations/overview).

## Assertion Components

### Trigger
A function that determines when an assertion should be executed. Triggers are registered with the PCL system to specify the conditions under which an assertion should be evaluated. There are several types of triggers:
- Call Triggers: Execute on specific contract calls
- Storage Triggers: Execute on storage changes
- Balance Triggers: Execute on ETH balance changes

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for detailed information about different trigger types.

### Pre-state/Post-state
Snapshots of the blockchain state captured before and after a transaction. These states are used by assertions to verify changes and enforce properties. The ability to compare pre and post states enables assertions to detect and prevent invalidating transactions that would result in undesired state changes.

Reshiram (V2) uses explicit `ForkId` snapshot reads. Legacy (V1) uses mutable fork switching. See the [Cheatcodes Reference](./cheatcodes-reference) for the supported interfaces.

### State Changes
Modifications to contract storage that occur during transaction execution. These can be tracked and verified using the Credible Layer's state change tracking capabilities, allowing assertions to monitor and prevent unauthorized modifications.

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for state tracking functions.

### Callstack

The sequence of function calls during a transaction. Assertions can inspect nested calls and state changes across contract boundaries.

### Assertion Bytecode
The compiled form of an assertion contract that is stored in the Assertion DA and executed by the PCL network.

See the [pcl Reference](/credible/cli-reference) for build and store commands.

### Assertion ID
A unique identifier for an assertion, computed as the Keccak256 hash of the assertion's EVM bytecode. The assertion ID is used to reference assertions in the Credible Layer protocol and retrieve assertion bytecode from the Assertion DA.

Learn more: [Assertion Data Availability](/credible/assertion-da#assertion-id)

### Assertion DA Prover Signature
A signature generated and returned by the Assertion DA as part of storing an assertion. This proof is used during deployment of the assertion to guarantee that the assertion bytecode is available on the Assertion DA.

Learn more: [Assertion Data Availability](/credible/assertion-da#assertion-da-prover-signature)

### Assertion Adopter
The contract that is being monitored by an assertion. This is the contract whose behavior the assertion is designed to verify.

### Assertion Group
A collection of assertions in the same contract that are related to the same protocol contract. This allows for organizing multiple assertions that protect different aspects of the same protocol.

### Assertion Function
A function in an assertion contract that performs a specific check. These functions must be registered in the `triggers()` function and are called by the PCL system when their trigger conditions are met.

## Development Tools

### `pcl`
The command-line tool for building, testing, and deploying assertions to the Credible Layer.

See the [pcl Reference](/credible/cli-reference) for all available commands.

### `phorge`
A minimal fork of Forge with functionality for assertion execution, used for testing and running assertions in the Credible Layer. It provides the infrastructure needed to compile, test, and deploy assertions.

### `credible-std`
The Phylax smart contract library that provides the base contracts and utilities for writing assertions. It includes the interfaces and implementations needed to interact with the Credible Layer's cheatcodes and assertion system.

### Cheatcodes
Special precompiles (similar to Ethereum's native precompiles) that provide additional capabilities for state manipulation, forking, and assertion management in the PhEVM environment. These are accessed through the credible-std library.

See the [Cheatcodes Reference](/credible/cheatcodes-reference) for a complete list of available cheatcodes and their usage.

### Test Environment
The PCL testing interface that extends Forge's testing capabilities with additional utilities specifically for testing assertions. It provides functions for adding assertions and validating transactions, making it easier to test assertion behavior in different scenarios.

Learn more about testing assertions in the [Testing Guide](/credible/testing-assertions).

### Backtesting
An automatic platform release check that tests every assertion in a release against transactions from the last 20,000 blocks. The result identifies historical transactions that the release would have invalidated so you can review false positives before deployment.

Learn more: [Backtesting](/credible/backtesting)

## Security Features

### Off-chain Execution
The ability to run complex security rules outside the main blockchain execution, providing significant efficiency gains compared to on-chain validation.

### Forced Inclusion Transactions
L2 transaction paths with protocol-level inclusion rules, such as L1-to-L2 deposits or delayed queues. Their assertion handling belongs to the [L2 integration policy](./l2-integrations/network-integration#transaction-source-coverage), not Ethereum builder routing.

### Circuit Breaker
An assertion pattern that collects value flowing into or out of a protected contract into one bucket per block, then limits the cumulative flow across those per-block buckets over a rolling window. Circuit breakers are useful when the goal is to reduce exploit velocity or contain blast radius rather than block one specific function call.

### Verifiability
The ability to inspect the rules and registry state behind a protocol's Credible Layer posture. Assertion IDs and registry entries are on-chain, while assertion bytecode is stored in Assertion DA. Public views expose the protocol's visible assertion posture; private project data remains restricted to authorized project users.

## Prevention

### Invalidation
A report that a candidate transaction violated an assertion. Production enforcement excludes the transaction at the integrated boundary. Alerting records the violation without blocking the live transaction; ordinary network validity and inclusion rules still apply.

Learn more: [Review and deploy changes](./managing-your-circuit-breakers#investigate-a-rejected-transaction)

### Revert
An EVM execution failure. An assertion revert occurs off-chain during validation and can cause builder exclusion. A guard revert occurs in the protocol execution path; if included on-chain, the transaction consumes gas. A caller may catch a subcall revert, depending on its code.

### Drop
Exclusion of a candidate transaction by a participating builder before inclusion. An excluded transaction consumes no on-chain execution gas. This differs from an included transaction reverting at a guard.

### Prevent
Blocking a rule-violating effect through the integrated enforcement path. Protection depends on active assertions, trigger coverage, builder behavior, and any required guards; a violation is not necessarily malicious.

## Assertion Lifecycle

### Apply
The process of creating a release on the platform using `pcl apply`. This command reads your `credible.toml` configuration, compiles assertion contracts, and creates a release. The platform handles storing assertion bytecode in [Assertion DA](/credible/glossary#assertion-da-data-availability) automatically.

Learn more: [Apply Assertions](/credible/apply-assertions) | [pcl Reference](/credible/cli-reference#apply)

### Deployment
The process of reviewing an assertion, linking it to a contract, and signing the transaction to deploy it on-chain. Deployment includes choosing whether to deploy to the Alerting or Production environment. The deployment transaction must succeed for the assertion to be deployed on-chain.

### Alerting
A mirrored chain environment used for testing assertions without affecting production. Assertions run in alerting mode to observe behavior, but transactions are not dropped if they break assertion rules. This allows protocol teams to test assertions safely before deploying to production.

### Production
The enforcement environment where participating Ethereum builders exclude candidates violating active assertions. Guard coverage and routing are also required for the protected operations; fail-open or bypass conditions can reduce mandatory protection.

### Timelock
A period enforced by the on-chain State Oracle contracts between an assertion change and when that change takes effect. The timelock applies when you add an assertion and when you remove one. It exists for two reasons: (1) to provide latency for the enforcer to index on-chain state and prepare for enforcement changes, and (2) to give users time to expect changes to protocol behavior. During the timelock period, newly added assertions are marked for enforcement or alerting but are not yet active, and removed assertions remain active until the timelock finishes.

### Marked for Enforcement
The state of an assertion deployed to production during the timelock period. The assertion is deployed but not yet actively preventing hacks. After the timelock expires, the assertion becomes enforced.

### Marked for Alerting
The state of an assertion deployed to alerting during the timelock period. The assertion is deployed but not yet running on the alerting environment. After the timelock expires, the assertion becomes active in alerting mode.

### Enforced
The state of an assertion in production after the timelock period has expired. An enforced assertion is active at the integrated enforcement boundary and causes violating candidate transactions to be excluded there. This term is only used for production assertions.

### Active in Alerting
The state of an assertion in alerting after the timelock period has expired. An assertion active in alerting mode is running on the mirrored chain environment, allowing protocol teams to observe how it behaves without transactions being dropped if they violate the assertion.

### Removal
The process of removing an assertion from active enforcement or alerting. Removal is scheduled through the State Oracle contracts and requires the configured timelock to expire before the assertion stops running in its selected environment.
