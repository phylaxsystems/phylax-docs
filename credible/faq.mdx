## Enforcement and Block Building

### When are transactions checked against my policies?

Participating builders run the Phylax enforcement engine while building a block. The engine simulates candidate transactions and evaluates the applicable assertions against their effects. Builders exclude candidates that violate active production rules.

Passing the checks makes a transaction eligible for inclusion; it does not guarantee selection, ordering, or finality. See [Ethereum Architecture](./architecture-overview).

### How does enforcement work when not every builder participates?

An onchain guard requires protected calls to execute in a credible block while its gate is active. An authorized builder records the block's marker in the Credible Registry. Protected calls in noncredible blocks revert, regardless of how they were submitted.

The Credible RPC routes transactions to participating builders. Configure the [actual transaction submitters](./dapp-integration#configure-transaction-submission) to use that route. Assertion validation is not part of Ethereum's consensus rules; enforcement depends on the builders and guards, including their configured recovery conditions.

### Is a credible-block marker proof that all assertions passed?

No. The marker records an authorized builder's attestation. It is not a cryptographic proof of assertion execution. The guard checks the marker; it does not execute assertions itself.

The model relies on authorized builders checking the applicable rules and binding the marker to the block they build. See the [Trust Model](./trust-model#decentralized-builders).

### What is the difference between the State Oracle and the Credible Registry?

The **State Oracle** records which assertions apply to which contracts, who can manage them, and when lifecycle changes take effect.

The **Credible Registry** records credible-block markers and controls which builders may submit them. Guards consult it to decide whether an operation may execute in the current block. Registering an assertion does not install a guard or configure transaction routing.

### What happens if a transaction calls several protocols or batches operations?

A transaction must pass all applicable assertions. One failure excludes the entire candidate transaction, including other operations in the same batch. It does not automatically exclude unrelated transactions or invalidate the whole block.

An onchain guard revert is different: a caller may catch a failed subcall and continue, depending on its code. Account for that behavior in batching, settlement, and retry logic.

### Does installing a Safe transaction guard cover modules too?

No. The Safe transaction guard covers the owner-authorized transaction path. Module execution is separate and needs its own reviewed control or an unavoidable downstream gate.

An assertion rejecting module activity at a participating builder does not prevent another builder from including an unguarded module transaction. See [Guard Testing](./testing-credible-block-guard).

## Routing and Transaction Outcomes

### Does the Credible RPC guarantee privacy, inclusion, or latency?

No. Routing delivers a transaction to the configured builder path. Privacy depends on the endpoint's forwarding and retention behavior. Inclusion and latency depend on participating builders, block opportunities, assertion workload, and retry behavior. Confirm and measure these properties for your deployment.

### Does a successful RPC simulation mean the transaction will pass assertions?

No. RPC simulation and assertion validation are separate checks. A simulation may account for the credible-block marker so guarded calls can be simulated without running the full production assertion set.

Even an assertion preflight result applies only to the simulated state. Active rules, ordering, and chain state can change before inclusion.

### Do rejected transactions consume gas?

A transaction excluded by a builder before inclusion consumes no onchain execution gas. An included transaction that reverts at a guard does consume gas. Guard and marker operations also have onchain costs, separate from offchain assertion execution.

### Are bridge, system, or forced-inclusion transactions protected?

On Ethereum, coverage depends on the submitted transaction and contract path. A bridge or relayer operation must reach the required guard, regardless of its caller or frontend.

L2 system transactions and forced-inclusion queues have separate network rules. See [L2 Transaction Source Coverage](./l2-integrations/network-integration#transaction-source-coverage).

### Does protection on one chain cover the same protocol on other chains?

No. Each chain needs its own supported integration, assertion deployment, and enforcement path. Deploying an assertion for one contract does not automatically protect its counterparts elsewhere. See [L2 and Sequencer Integrations](./l2-integrations/overview) for the separate network model.

## Authority and Rule Changes

### What can a compromised assertion manager do?

A compromised manager can use its lifecycle permissions to propose restrictive rules or remove protections, subject to authorization and timing rules. This can affect availability or weaken protection; the role does not itself grant permission to transfer protocol assets.

Assertion timelocks do not necessarily constrain separate guard, upgrade, guardian, or Registry-admin powers. See [Authority Boundaries](./trust-model#authority-boundaries) for those distinctions.

### Which rules apply while an update is pending?

Existing assertions remain active until their scheduled removal takes effect. New assertions begin applying after their activation delay. The State Oracle determines those times.

Review additions and removals together to avoid a gap in protection or conflicting rules during the transition. Guard changes and protocol upgrades follow their own authorization and timing. See [Deploy Assertions](./deploy-assertions-dapp#step-4-deploy-the-assertion).

## Availability, False Positives, and Recovery

### What happens if participating builders stop producing credible blocks?

While the gate remains active, protected operations cannot succeed in noncredible blocks. A configured fail-open condition can restore access after a gap in credible blocks. The block-gap condition opens only when the gap is **greater than** the configured threshold.

Fail-open relaxes the guard's block requirement. Existing protocol checks still apply, and participating builders can continue enforcing assertions, but transactions may also execute through builders that do not run them.

A block-gap fallback does not resolve a restrictive rule when builders continue producing credible blocks. Use the recovery procedure agreed for your integration; see [Recovery Testing](./testing-strategy#5-rehearse-recovery).

### Do all guards handle Registry failures the same way?

No. The Safe guard includes fail-open handling for failed or malformed Registry responses. The generic contract guard does not provide the same catch-and-continue behavior; a failed Registry read can revert the protected call.

Check the deployed implementation, including overrides and bypass permissions. A builder outage, a Registry read failure, and a restrictive assertion can require different recovery actions.

### How does approving one transaction differ from raising a limit?

A reviewed exception authorizes a specific transaction through your protocol's approval process. Raising a threshold changes what the policy permits for other transactions too. Resetting a counter, disabling an assertion, and bypassing a guard each have different effects on protection.

Review the scope, duration, and restoration of protection for the action your integration supports.

### Will a rejected transaction automatically run after we fix the rule?

No. Exclusion does not put a transaction in an onchain queue. The submitting wallet, relayer, or service determines whether to retry.

Before retrying, recheck nonce, expiry, state, slippage, and whether the action is still appropriate. See [Managing Your Circuit Breakers](./managing-your-circuit-breakers#investigate-a-rejected-transaction) for investigating the rejection.
