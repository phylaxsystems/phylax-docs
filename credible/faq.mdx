## General Questions

### What is the Phylax Credible Layer?
The Credible Layer checks protocol-defined assertions before block inclusion. Enforcement uses either an integrated rollup sequencing path or participating builders combined with an application guard. See the [overview](./credible-layer-overview).

### Why do I need the Credible Layer when I can write rules in my contracts?
Assertions run off-chain and can inspect candidate execution state using supported assertion capabilities. They let you express rules separately from application code. Eligible contracts on covered rollup paths can adopt assertions without modification; Ethereum requires a direct guard or supported hook/adapter. Off-chain evaluation has resource costs, and there is no universal performance multiplier.

### How does the Credible Layer differ from other security approaches?
It supplies protocol-authored checks to the transaction-building process before inclusion. The inclusion boundary and availability tradeoffs depend on the [enforcement design](./credible-layer-overview#why-the-designs-differ). It complements contract checks and audits; it only covers behaviors expressed by applicable assertions.

### What's the difference between assertions and traditional audits?
Audits review code; the Credible Layer evaluates applicable rules during transaction building on integrated paths. Its coverage depends on the assertions and the enforcement boundary.

### What is The Phylax Explorer?
**[The Phylax Explorer](/credible/dapp-explorer)** is the public dashboard that displays the security and operational risk posture of protocols that have opted into runtime enforcement.

Users can find summaries of actions protected by circuit breakers and assertions, scenarios the assertions prevent, operational details for admin multisig wallets, upgradeability documentation, and whether the currently deployed protocol has meaningfully diverged from the code at the time of audit.

**Learn More:**
- [Deploy Assertions](/credible/deploy-assertions-dapp)
- [Glossary - The Phylax Explorer](/credible/glossary#the-phylax-explorer)

### Is the Credible Layer a SaaS protocol?
No. The Credible Layer is a protocol with product tools around it: the platform and `pcl` help teams author, review, deploy, and monitor assertions, while the on-chain registry remains the source of truth for active assertion state.

Access to assertion management is still gated by authorization. Only verified protocol admins can attach assertions to protected contracts, and supported networks may have onboarding or availability constraints.

## Technical Details

### What exactly is an assertion?
An assertion is a Solidity contract that checks a protocol-defined property against candidate transaction behavior. A failed `require` can signal a violation. Passing establishes that the evaluated rule held, not that the transaction is safe in every respect or guaranteed inclusion. A violation is not automatically an exploit. See [Assertions Overview](./assertions-overview).

### What are invariants and why are they important?

Invariants are properties of your protocol that you want to maintain.
They are fundamental to the Credible Layer's approach to security, and assertions are our tool to let you enforce them.
While invariants define what should always be true, assertions give you the practical means to check these rules on the integration’s covered paths:

1. **Definition**:
   - Properties that must hold true throughout execution
   - Core rules that define valid and invalid protocol states
   - Security guarantees that shouldn't be violated
2. **Common Examples**:
   - Total supply must equal sum of all balances
   - Pool balance should never drop below initial deposit
   - Admin privileges can't be granted without proper authorization
   - Price changes must stay within acceptable bounds
3. **Advantages**:
   - Easier to reason about security properties
   - Path Independent: Any state transition that breaks the invariant is flagged

For a good explainer on invariants see [this article](https://blog.trailofbits.com/2025/02/12/the-call-for-invariant-driven-development/)

**Learn More:**

### How do assertions work?

Although assertion IDs and registry entries are stored on-chain for transparency, assertions are run off-chain through the PhEVM (Phylax EVM) by the sequencer or block builder for performance reasons and can:

1. Compare state before and after transactions
2. Monitor specific function calls
3. Track changes to storage slots
4. Analyze transaction patterns
5. Enforce protocol-wide invariants

### What counts as an assertion failure?
An assertion violation means an evaluated rule failed. An evaluator error means validation could not complete reliably. The builder or sequencer applies its documented policy; neither outcome by itself proves an exploit. A guarded call reverting on-chain is a separate event. See [General Design](./architecture-overview#assertion-validation-process).

### What are cheatcodes and how do they help?

Cheatcodes are special functions provided by the PhEVM that give assertions powerful capabilities
beyond standard Solidity.

For detailed documentation and examples of all available cheatcodes, see our
[Cheatcodes Reference Guide](/credible/cheatcodes-reference).

### How do I edit assertions?
Edit and test the assertion, create a replacement release, and review the additions and removals before deployment. Each change takes effect under the configured State Oracle lifecycle. Plan activation and deactivation to avoid unintended coverage gaps. See [Apply Assertions](./apply-assertions).

### Can I copy assertions from other protocols?
Yes, you can copy and adapt assertions from other protocols and use them to protect your own protocol.
You should make sure that the assertions are compatible with your protocol.
It will make the most sense to copy assertions for standard libraries and interfaces.
You can inspect public assertion posture in The Phylax Explorer. Some project and invalidation details are only visible to project managers and collaborators.

## Implementation and Adoption

### How does the Credible Layer work at the sequencer level?
An integrated sequencing path supplies candidate execution context to the evaluator and uses the verdict before inclusion. Violating candidates can be excluded on covered paths. See [Rollup Sequencer Integrations](./network-integrations/rollup-sequencers).

### How does the Credible Layer work with decentralized sequencers?
Coverage depends on which components control inclusion and how alternate producers are constrained. Integrating one producer does not automatically constrain the others. Enshrining assertions in consensus would be a separate design, not a guarantee of these integrations. See [Ethereum / Participating Builders](./network-integrations/architecture-ethereum) for the guard-based design.

### How are externally originated transactions handled?

Network integrations define validation policy for transactions that do not enter through ordinary user RPC flow, such as bridge-originated actions, delayed queues, scheduled system transactions, or forced-inclusion-style paths. The policy specifies where assertion validation runs, how results are routed into sequencing or block-building components, what timeout behavior applies, and which invalidation context is sent to affected protocols.

**Learn More:**
- [Network Integration Overview - Transaction Source Coverage](/credible/network-integration#transaction-source-coverage)
- [Glossary - Forced Inclusion Transactions](/credible/glossary#forced-inclusion-transactions)

### Does the Credible Layer introduce new trust assumptions or centralization points?
Yes, there are integration-specific dependencies and authorities to assess. Rollup users rely on the operator honoring assertions on covered sequencing paths. Ethereum users additionally rely on authorized marker operators correctly enforcing applicable assertions, registry administration, and application guard configuration. Assertion availability and policy-management authority also matter. See [Trust Model](./trust-model).

### Is this a form of censorship?
Assertions restrict application behavior according to an authorized protocol policy. That does not eliminate censorship risk: operators can still omit transactions, and privileged policy or guard changes can affect access. The Ethereum guard’s global liveness signal does not protect against selective censorship. See [Neutrality](./neutrality).

### Does the Credible Layer slow down the network?

The Credible Layer is designed to keep assertion overhead bounded and off the serial block-building path where the network integration supports that model. The hot path should mainly pay for tracing, assertion routing, checkpointing, and work submission, while assertion execution can run in parallel worker capacity.

The practical requirement is that assertion workers keep up with the transaction workload. If assertion execution falls behind, the integration needs bounded backpressure, publication-boundary waiting, or another network-specific policy.

**Learn More:**
- [Assertion Enforcer - Performance Model](/credible/assertion-enforcer#performance-model)
- [Architecture](/credible/architecture-overview)

### How do you extend the validation logic of the sequencer to the platform?
The platform coordinates assertion releases; it does not control block inclusion. The integrated sequencer obtains evaluation results and applies them during transaction building. Eligible contracts need no guard for covered rollup paths. Ethereum has a different [application integration requirement](./network-integrations/architecture-ethereum#direct-guard-or-adapter).

### Can anyone write assertions for my contracts?
Anyone can author code, but registering and managing assertions requires the applicable authorization. Initial contract authorization, ongoing State Oracle manager authority, platform permissions, and administrative overrides are distinct. See [Ownership Verification](./ownership-verification).

### My protocol doesn't support the owner interface. Can I still use the Credible Layer?
On supported rollups, eligible contracts can use [manual verification](./manual-verification). Ethereum requires a supported direct or hook/adapter integration and its matching authorization path. Manual verification alone cannot make an unguarded Ethereum contract require participating builders.

### How can you write rules for immutable contracts?
On supported rollup deployments, the integrated sequencer can exclude violating candidates on covered paths without changing the contract. This does not establish coverage for forced inclusion or fallback production. On Ethereum, an existing mandatory hook may support an adapter, but arbitrary immutable contracts with unguarded paths cannot be promised mandatory protection.

### What are the ramifications of writing rules for supposedly immutable contracts?
The bytecode can remain immutable while assertion policy changes which transactions the integrated sequencer retains. Users should inspect who can change that policy, the activation delay, and routes outside enforcement. See [Ownership Verification](./ownership-verification) and [Trust Model](./trust-model).

### What's the difference between Staging and Production environments?
Where supported, staging observes assertion outcomes without excluding transactions because of those assertions. Production applies active assertions on the integration’s enforced paths. State Oracle activation and code availability are separate from creating a release. Staging availability and backend capabilities must be confirmed for the target deployment; an Ethereum application guard has its own behavior independent of staging labels.

### What happens if credible block production stops?

For the generic Ethereum guard, the credible-block requirement relaxes only when the block gap is strictly greater than the configured threshold. The default is 10 blocks at the [documented source revision](./ethereum-guard-reference). Registry read failures and caller bypasses have separate behavior. This restores baseline operation, not equivalent assertion protection. Rollup fallback is a separate sequencer policy.

### Does passing simulation guarantee inclusion?

No. [Credible RPC](./ethereum-rpc-integration) simulation occurs before signing; the builder still evaluates the candidate in its actual execution context. Submission acceptance, builder evaluation, and canonical inclusion are separate outcomes.

### How long is the timelock period?

The timelock period exists for two reasons: (1) to provide latency for the enforcer to index on-chain state and prepare for enforcement, and (2) to give users time to expect changes to protocol behavior. The exact duration may vary because it is configured on the State Oracle smart contracts. The same model applies when assertions are removed: the change is scheduled on-chain first, then only takes effect after the configured timelock expires.

## Practical Questions

### What are some example use cases for assertions?
1. **DeFi Protection**
   - Prevent flash loan attacks
   - Monitor liquidity pool ratios
   - Enforce borrowing limits
   - Detect price manipulation
2. **Governance Safety**
   - Validate proposal execution
   - Monitor admin actions
   - Enforce timelock requirements
   - Track parameter changes
3. **Cross-Protocol Security**
   - Monitor oracle data feeds
   - Track cross-chain messages
   - Validate bridge transactions
   - Enforce protocol dependencies

### How do I test my assertions?

Testing assertions is similar to standard Forge testing, with additional Credible Layer-specific features:

1. **Standard Testing Tools**:
   - Use familiar Forge assertions (`assertEq`, `assertTrue`)
   - Access standard cheatcodes (`vm.prank`, `vm.deal`)
   - Leverage console logging for debugging

2. **Credible Layer-Specific Testing**:
   - Register assertion function to be run on the next transaction using `cl.assertion()`
   - Test both positive and negative cases
   - Verify assertion behavior across different scenarios

For detailed examples and testing patterns, see our [Testing Guide](/credible/testing-assertions).
