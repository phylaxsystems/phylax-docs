---
title: 'How to Plan Ethereum Assertion Testing'
description: 'Validate assertion logic, release evidence, Ethereum guards, RPC routing, and recovery before production.'
---

Test assertion logic, builder enforcement, guards, and transaction routing. Alerting checks rule behavior but does not exercise every production dependency.

## Prerequisites

Identify the protected contracts and entry points, assertion specification, intended guard implementation, transaction submitters, Protocol Manager, and recovery roles. Confirm the test environment available for the deployment; alerting is not itself a public Ethereum testnet.

## 1. Test Rules Locally

Use [local assertion tests](./testing-assertions) for allowed actions and intended failures. Cover trigger matching, snapshot selection, boundary values, gas limits, and exceptional legitimate operations such as migrations and upgrades.

Include a failure case that would pass if the assertion were absent. A test that only observes the protocol's existing revert does not demonstrate added assertion protection. Reuse protocol fixtures and add focused regression tests for findings from alerting or historical replay.

## 2. Review the Release Evidence

Creating a release with `pcl apply` starts the platform's verification, source-code, and backtesting checks. Review the actual target contracts and assertion changes, then investigate each backtesting finding before deployment.

A clean backtest applies only to the tested history and replay conditions. See [Backtesting](./backtesting) and [Review and Deploy Policies](./deploy-assertions-dapp#step-4-review-release-checks).

## 3. Observe Alerting Behavior

Deploy the reviewed release to alerting on the [Ethereum platform](https://ethereum.phylax.systems). Wait for the configured activation time and monitor matching activity and invalidations.

Test ordinary activity and legitimate exceptions. Check that transactions exercised the assertions. Choose the review period based on the scenarios covered.

Investigate false positives, add local regression cases, and review a new release after changes. Alerting does not drop live transactions, so it does not prove that production rejection or recovery works.

## 4. Test Guards and the Submission Path

Use local or fork-based guard tests, then the approved end-to-end environment with the real integration path.

| Scenario | Evidence to collect |
| --- | --- |
| Allowed transaction in a credible block | Marker present before the operation, correct guard decision, and expected protocol state change. |
| Candidate failing an active assertion | Assertion result and invalidation evidence, exclusion by the participating builder, and unchanged protected state. |
| Protected operation in a noncredible block | Guard rejection while fail-open and bypass conditions are inactive. |
| Alternative entry point or Safe module | The intended on-chain gate is unavoidable, or the gap is explicitly excluded from coverage. |
| RPC simulation and actual submission | The submitter uses the intended endpoint and the actual builder result agrees with the tested expectation. |
| Batch containing a protected operation | Expected whole-transaction rejection or on-chain subcall handling, with application reconciliation. |
| Guard or protocol upgrade | Correct wiring, storage layout where relevant, and preserved coverage after the change. |

A timeout alone is not rejection evidence. Check transaction status, builder or platform evidence, and contract state. Distinguish a pre-inclusion exclusion from an included guard revert, which consumes gas.

See [Guard Testing](./testing-credible-block-guard) for the local harness. Its fixture proves the harness behavior; target your actual contract to validate its integration.

## 5. Rehearse Recovery

Test the configured fail-open boundary, Registry-read failures, authorized bypasses, assertion changes, and manager recovery. Use the exact guard implementation: Safe and generic contract guards do not handle Registry failures identically.

Test restrictive assertions while builders continue producing credible blocks. This scenario may never trigger a block-gap fallback. Verify that recovery remains authorized and executable, then test safe resubmission or reconciliation of excluded operations.

## 6. Review Production Readiness

Resolve findings from the tests above before production. Record coverage gaps, activation delays, and conditions that reduce enforcement.

Complete the [integration plan](./dapp-integration), including monitoring and recovery responsibilities.
