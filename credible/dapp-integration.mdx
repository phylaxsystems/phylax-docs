Plan guard coverage, transaction routing, and recovery with your [FDE](./work-with-phylax). Use this checklist before [deployment](./deploy-assertions-dapp).

## Prerequisites

Agree on the policy scope and review responsibilities. Identify the protected contracts, policy signers, and transaction submitters. Confirm the network, supported assertion specification, and test environment.

## Adoption Workflow

Your team approves the policies and exceptions. Engineers implement and test assertions, then prepare a release with `pcl apply`. Your signers authorize activation.

See [Work with Phylax](./work-with-phylax#the-integration-process) for the delivery process.

## What You Control

Your team controls policy assignments, deployment environments, and notification settings. Deployment authority remains separate from project membership and protocol administration.

## Map Coverage and Required Contract Changes

Identify the protected operations, relevant state, dependencies, and coverage gaps. Every protected execution path must reach a suitable guard.

Choose the integration path that fits the contract:

| Contract structure | Integration |
| --- | --- |
| You can change the implementation | Inherit [Credible Block Guard](./credible-layer-contracts#credible-block-guard) and guard the protected entry points. |
| A compatible proxy can change its implementation target | Install [Credible Proxy](./credible-layer-contracts#credible-proxy) with the protected selectors. UUPS proxies are not supported. |
| Operations use Safe owner transactions | Install [Credible Safe Guard](./credible-layer-contracts#credible-safe-guard). Review module paths separately. |
| The protocol exposes an unavoidable hook | Call an [Assertion Adapter](./credible-layer-contracts#assertion-adapter) and attach assertions to it. |

Include alternative entry points, internal dispatch, and wallet modules. A guarded selector does not protect another selector that reaches the same operation. Resolve unguarded paths before claiming coverage.

Assign responsibility for contract changes and review the deployed version. Include guard replacement, proxy configuration, and bypass permissions. These remain separate from the Protocol Manager wallet that signs policy releases.

## Configure Transaction Submission

Configure the Credible RPC on each top-level submitter of protected transactions. This includes automated submitters and multisig executors. Off-chain signers and internally called contracts do not select the route.

Ordinary reads and unprotected traffic can retain their existing providers. Test actual submission separately from RPC simulation. The Registry permits [zero-gas-price simulations](./credible-layer-contracts#zero-gas-price-calls), so simulation success does not establish that a paid transaction passes the guard or active assertions.

For L2 queues and forced inclusion, see [L2 Integration Planning](./l2-integrations/network-integration#transaction-source-coverage).

## Authorization Requirements

Confirm the Protocol Manager for each contract through [Managing Policy Deployments](./managing-policy-deployments). Record the signing policy, recovery path, and deployed delays for each privileged role.

## Deployment Modes

- **Alerting** records violations in a mirrored environment without blocking live transactions. It does not test every production guard or route.
- **Production** enforces active policies through participating builders. Protected operations require configured guards and routing.

## Test Availability and Recovery

Follow the [testing strategy](./testing-strategy) and [guard tests](./testing-credible-block-guard). Include blocked recovery transactions and lost keys.

A block-gap fallback may not resolve false positives if credible blocks continue. Define how submitters investigate exclusions and retry. Do not assume automatic resubmission.

## What Users Can Verify

Users can inspect active policies and onchain state. Where public [Explorer views](./dapp-explorer) are available, they show selected protection details. Private transaction traces require project access.

## What Successful Rollout Looks Like

Activate production after policy, guard, routing, and recovery tests pass. Assign responsibility for alerts, policy changes, and periods of reduced enforcement.
