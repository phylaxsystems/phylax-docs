title: Function Call Inputs
description: Inspect recorded call arguments and reconcile them with explicit state snapshots.

Call-input inspection supplies the arguments recorded for a target and selector. Use it to compare an expected state transition with the actual storage change.

## Status

**Spec:** Reshiram in the example below. **Evidence:** locally tested fixture. **Scope:** ordinary successful `CALL` operations to a counter with a `uint256` in slot zero.

## API and behavior

`getCallInputs(target, selector)` returns `PhEvm.CallInputs[]` for `CALL` operations. `input` contains the ABI-encoded arguments without the function selector. Each record has a call `id` for explicit pre- and post-call snapshots. Use the opcode-specific alternatives in the [API reference](../cheatcodes-reference#getcallinputs) for other call types.

`CallInputsAssertion` below adds each recorded `add(uint256)` argument to the pre-transaction counter, then compares the sum with the post-transaction slot. Bookkeeping stays in local memory; a `view` assertion does not write its own storage.

This establishes local behavior, not production dispatch or historical exploit prevention.

## Coverage limits

The tests cover two nested additions, an unaccounted write, and an unrelated call. They do not establish behavior for reverted child calls, delegatecalls, proxies, or alternate mutation paths. Adapt both the call selection and accounting model before using this pattern for balances or shares.

Endpoint equality does not rule out an invalid intermediate state. For policies around individual operations, use [Call Frame Context](./call-frame-context). For parameter-dependent storage slots, derive the key from the ABI and storage layout or use [Modified Key Discovery](./modified-keys) within its documented limits.
