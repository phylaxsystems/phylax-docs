title: 'Ownership Verification'
description: 'How the Credible Layer authorizes assertion management for a contract.'
---

Ownership verification establishes who may manage assertions for a protected contract. The supported verifier and registration process depend on the deployment and the contract's ownership design.

## Protocol Manager Authorization

The State Oracle associates a Protocol Manager with registered contracts. This address can perform the assertion lifecycle actions permitted by that deployment. Anyone can author assertion code; only authorized accounts can activate it for the registered contracts.

Possible authorization paths include a supported ownership interface such as `owner()`, an explicit initial Protocol Manager interface, or an approved manual registration process. Confirm the supported path before changing protocol contracts. A contract does not always need to expose `owner()` to integrate.

## Manual Verification

For existing contracts that do not fit a supported automatic verifier, Phylax can review evidence of protocol control and the intended manager address. Availability and requirements must be confirmed for the target deployment. Ethereum integration is not categorically excluded from this path.

Approval establishes assertion-management authority for the agreed contracts. It does not install guards, configure RPC routing, or prove that all intended operations are protected. See [How to Request Manual Verification](./manual-verification).

## Separate Authorities

Platform project membership, Protocol Manager authority, transaction submission, protocol upgrades, and guard administration are distinct permissions. A wallet used by a backend to submit transactions need not control assertion policy.

A manager can make changes that affect availability and protection, subject to the configured lifecycle. Secure this role with an appropriate signing policy and review how it can be recovered or transferred. Check the deployed authorization and timing rules rather than assuming a fixed delay.

See [Trust Model](./trust-model) for compromise and recovery considerations, and [Integration Planning](./dapp-integration) for rollout requirements.
