The Credible Layer uses admin verifier modules to determine who can deploy assertions for a contract. Most deployments use owner-based verification by default. This design will continue to expand with additional ownership patterns.

<Note>
This page explains the ownership model. If your rollup contracts do not fit the default verifier and you need the process for getting approved, use [How to Request Manual Verification](./manual-verification). Manual verification is not available for Ethereum mainnet contracts.
</Note>

## Current Implementation

The common default verifier expects contracts to implement the `owner()` function (Ownable pattern). Here's an example of the expected interface:

```solidity
interface IOwnable {
    function owner() external view returns (address);
}
```

Use the admin verifier supported by your deployment. An `owner()` check can authorize initial registration; it is not necessarily the source of ongoing State Oracle manager authority. Ethereum adapters can expose a bootstrap manager interface; match it to the deployed verifier.

<Note>
Managing assertions is a sensitive role. We recommend using hardware wallets and multisig accounts for protocol admin (assertion manager) addresses.
</Note>

## Manual Verification (Overview)

If your contracts are deployed on a supported rollup and are immutable or don't expose an admin interface, you may be able to request manual verification. In this path, Phylax validates that the requesting team controls the protocol and then registers a protocol admin (manager) address for the specific contracts in the State Oracle registry.

Manual verification is not the Ethereum adoption path. The distinction is enforcement authority, not a universal L1/L2 rule; see [Ethereum Integration](./network-integrations/architecture-ethereum).

High-level requirements and signals include:
- Demonstrated control over the protocol codebase (e.g., ability to merge to the official repo and manage collaborators)
- Strong public proof that the protocol wants to use the Credible Layer and that the selected admin address reflects the organization's intent (e.g., multisig signatures or official social announcements)
- Willingness to share identity or evidence when needed

After approval, the protocol admin address is added to the registry and a timelock begins before assertions can be deployed. Protocols can also opt out of registry additions if they do not want assertions attached to their contracts.

See [How to Request Manual Verification](./manual-verification) for the full process and requirements.

## Separate Authorities

Platform membership controls product access. Initial contract authorization establishes who can register an adopter. After registration, the State Oracle’s manager record controls ordinary assertion lifecycle operations, subject to its administrative roles and restrictions.

The Credible Registry separately controls builder authorization. Application ownership, upgrade permissions, and guard bypass setters remain application authorities. A manager transfer or platform invitation does not automatically transfer those powers. Exact permissions depend on the [contract version](./credible-layer-contracts).
