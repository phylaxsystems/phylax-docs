Test assertions locally with `CredibleTest` and the Forge test utilities. Use the [testing strategy](./testing-strategy) for integration tests and production readiness.

## Prerequisites

Use a project with [PCL installed](./credible-install), a pinned `credible-std` dependency, the assertion under test, and protocol fixtures. Run commands from the project root using the assertion test profile configured in `foundry.toml`; see [profile configuration](./ci-cd-integration#foundry-profile-configuration).

For a complete first exercise, use [Run an Example Policy Locally](./pcl-quickstart). The patterns below assume you already have a test project.

## Register an Assertion for the Next External Call

The interface below explains the harness mechanism. In your test project, import `CredibleTest` from your pinned `credible-std` dependency, as the next example does; do not create a second local definition.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.13;

import {Vm} from "../lib/forge-std/src/Vm.sol";

interface VmEx is Vm {
    function assertion(address adopter, bytes calldata createData, bytes4 fnSelector) external;
}

contract CredibleTest {
    VmEx public constant cl = VmEx(address(uint160(uint256(keccak256("hevm cheat code")))));
}
```

## Using the Testing Interface

This example uses the contracts and layout from the [pinned starter tutorial](./pcl-quickstart). In another project, substitute your own target, assertion, imports, and expected failure. A test registers the assertion, calls the protocol, and checks the result:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.13;

import {OwnableAssertion} from "../src/OwnableAssertion.a.sol";
import {Ownable} from "../../src/Ownable.sol";
import {CredibleTest} from "credible-std/CredibleTest.sol";
import {Test} from "forge-std/Test.sol";

contract TestOwnableAssertion is CredibleTest, Test {
    // Contract state variables
    Ownable public assertionAdopter;
    address public initialOwner = address(0xf00);
    address public newOwner = address(0xdeadbeef);

    // Set up the test environment
    function setUp() public {
        assertionAdopter = new Ownable(initialOwner);
        vm.deal(initialOwner, 1 ether);
    }

    // Test case: Ownership changes should trigger the assertion
    function test_assertionOwnershipChanged() public {
        assertEq(assertionAdopter.owner(), initialOwner);

        cl.assertion({
            adopter: address(assertionAdopter), // Address of the contract to protect
            createData: type(OwnableAssertion).creationCode, // Bytecode of the assertion contract
            fnSelector: OwnableAssertion.assertionOwnershipChange.selector // Selector of the assertion function to run
        });

        // Simulate a transaction that changes ownership
        vm.prank(initialOwner);
        vm.expectRevert("Ownership has changed");
        assertionAdopter.transferOwnership(newOwner); // This will trigger the assertion

        // Check that owner didn't change
        assertEq(assertionAdopter.owner(), initialOwner);
    }
}
```

<Note>
Local assertion tests use reverts to model rejection by a participating builder. They do not exercise Ethereum block markers, guard coverage, or RPC routing; test those with the [integration testing plan](./testing-strategy). See [Local Testing vs. Production](./execution-model) for details.
</Note>

`cl.assertion()` registers one assertion function for the next monitored external call. Its trigger must match that call. Use `vm.prank()` to select the caller and `vm.expectRevert()` to check the expected failure. Successful transactions retain their state changes.

### Testing Assertion Contracts with Constructor Arguments

Use `ph.getAssertionAdopter()` inside an assertion function to obtain its assigned contract; it is unavailable in the constructor. If your assertion declares constructor arguments, append their ABI encoding to the creation bytecode in the exact declared order. The following fragment illustrates an assertion with one address argument; only use it if that constructor exists:

```solidity
createData: abi.encodePacked(type(OwnableAssertion).creationCode, abi.encode(address(token)))
```

## Testing Patterns

### Batch Operation Testing Pattern

Use a helper contract to execute several operations in one transaction. Check their cumulative effect on the final state.

```solidity
// Helper contract that performs multiple operations
contract BatchOperations {
    TargetContract public target;

    constructor(address target_) {
        target = TargetContract(target_);
    }

    function batchOperations() external {
        // Perform multiple operations in a single transaction
        target.deposit(100);
        target.deposit(200);
        target.deposit(300);
    }
}

// Test function
function testMultipleOperations() public {
    // Regular test setup omitted for brevity
    
    // Create helper contract
    BatchOperations batch = new BatchOperations(address(target));

    // cl.assertion() omitted for brevity

    // Execute all operations in one transaction
    batch.batchOperations();
}
```

<Note>
Prefer the helper function above. A fallback call through `address(batchUpdater).call("")` does not propagate revert data automatically. If you use it, check the result explicitly:

```solidity
(bool success,) = address(batchUpdater).call(""); // Empty calldata triggers fallback
require(!success, "assertion reason");
```
</Note>

See [Deposit Supply Delta](../assertions-book/assertions/ass08-sum-of-all-positions) for an example.

### Protocol Mocking

Use a mock protocol to create states that the real protocol's checks prevent. For example, expose a balance change that should make the assertion fail.

See the [credible-std examples](https://github.com/phylaxsystems/credible-std/tree/fe49de6dcddb8ea1f77ea2828a0c9d7d5f923db0/examples/assertions-book) for mocks.

## Gas Limits

Assertion execution has a runtime-configured gas budget. Obtain the active budget from the deployment operator and test the maximum expected workload against it; do not infer it from the local EVM block gas limit.

Exceeding the limit causes `OutOfGas` and invalidates the candidate, even if the intended policy condition would pass. This prevents attackers from bypassing validation through expensive inputs. Test the maximum expected workload.

### The Happy Path Problem

Successful checks often cost more gas because loops and checks run to completion. Failure cases can exit early.

Match the compiler and optimizer settings used for deployment. The `credible-std` protection tests use `FOUNDRY_PROFILE=ci`, which enables optimization. With the reviewed library and PCL 1.6.0, the Safe configuration test with 32 modules exceeds the assertion gas limit under the default unoptimized profile and passes under `ci`.

### Testing Recommendations

- Test with realistic data volumes - if your assertion loops through items, test with the maximum expected count
- Test batch operations at maximum expected size
- Use `pcl test -vvv` to monitor gas usage
- If approaching the limit, optimize or split the assertion

## Run and Verify Your Tests

Run `pcl test` with your project's assertion profile. Use `--match-contract` or `--match-test` to isolate a case, then run the full assertion suite before preparing a release.

Check that the intended assertion function executed, allowed operations retained their expected state changes, and rejected operations failed for the expected assertion reason. A test passing because the protocol reverted before the assertion ran does not validate that assertion. Include legitimate exceptions and maximum-workload cases.

When the results match the approved policy, [prepare a release](./apply-assertions). If a case fails unexpectedly, use [Troubleshooting](./troubleshooting) before continuing.
