These requirements are for builder and sequencer operators. Protocol teams using the Ethereum platform and RPC do not need to run their own builder or enforcer. Size assertion execution against the actual node workload and [integration architecture](./assertion-enforcer#integration-architecture); a sidecar is not required.

## Production Guidance

Sizing depends on network throughput and assertion complexity. Use these guidelines as a starting point and scale based on load testing:

| Component | Guidance |
|-----------|----------|
| **CPU** | High-core, modern server CPU |
| **RAM** | Sufficient memory for state caches and execution |
| **Storage** | Fast local SSD with headroom for growth |
| **Network** | Reliable access to required RPC and assertion data endpoints |

### CPU

Budget assertion workers alongside transaction execution. Measure peak trigger volume and tail latency on the chosen client and hardware before setting worker counts or admission limits; there is no workload-independent core count in this guide.

### Memory

Allocate enough RAM for state caches and execution overhead. Exact requirements vary by chain size and assertion complexity.

### Storage

Use fast local (not networked) SSDs to keep I/O latency low. Budget for sustained IOPS and headroom for state growth.

### Networking

For an embedded library, validation does not require a separate network hop from the builder. If maintaining a separate validation service, measure round-trip latency and state-transfer costs within the block-production budget.

**Key requirements:**
- For a separate service, a low-latency link between the node and validation workers
- Prefer private networking; avoid routing over the public internet
- Stable egress to chain RPC and assertion data endpoints

## Local Development

Use the [local tutorial](./pcl-quickstart) to run assertion tests. Local test results do not establish production capacity; benchmark with the intended client, assertions, and transaction workload.
