---
title: 'Assertion Data Availability'
description: 'Where Ethereum builders and the Linea sidecar obtain assertion bytecode and how they check its integrity.'
---

Ethereum mainnet provides data availability (DA) for assertion bytecode. Builders populate their local Assertion Stores from L1 registration events. On Linea, the sidecar retrieves the bytecode from the offchain Assertion DA service operated by Phylax.

<span id="purpose" />
<span id="key-concepts" />

## Assertion ID

Both integrations identify the creation data by the same hash.

```text
Assertion ID = Keccak256(Creation_Bytecode ++ Encoded_Constructor_Arguments)
```

For an assertion without constructor arguments, the ID is the hash of the creation bytecode alone. The State Oracle records which adopter the artifact applies to and when it becomes active.

<span id="current-implementation" />
<span id="how-it-works" />

## Ethereum Mainnet

### Storing Assertions

[`pcl apply`](./apply-assertions) prepares a platform release for review, including [source verification](./deploy-assertions-dapp#source-code). The authorized Protocol Manager publishes the creation data on L1 when registering the assertion.

The State Oracle's `addAssertion` call carries the full creation data in its `proof` argument. The onchain DA verifier checks `keccak256(proof) == assertionId`. The State Oracle then emits the same bytes in its `AssertionAdded` event. For example, log 458 in [this mainnet registration](https://etherscan.io/tx/0x3e9f0b77dfad8a589e6d029b8b43ebb369dd375700acc204c123748c3039bd97#eventlog) contains 7,155 bytes of creation data in `proof`.

### Retrieving Assertions

The builder reads the event from the configured State Oracle. It checks the verifier address and confirms that the hash of the proof matches the assertion ID. It then prepares the assertion from those bytes and records the assignment and activation block in its local Assertion Store. The Assertion Enforcer reads that store during block building. See [For Ethereum Builders](./ethereum-builder-integration).

<span id="design-rationale" />

## Linea

<span id="why-off-chain-storage" />
<span id="why-compilation-happens-off-chain" />

The offchain DA service compiles the submitted Solidity source and stores the creation bytecode and encoded constructor arguments separately. The Linea sidecar indexes onchain assignments, fetches the corresponding artifact by assertion ID, and combines the bytecode and arguments to check the hash. It caches the prepared assertion locally for enforcement. See [Linea / Besu Integration](./l2-integrations/architecture-linea).

### Assertion DA Prover Signature

The service signs the assertion ID when it stores the artifact. Linea uses that signature as its availability proof, which keeps the registration transaction small even for a large assertion. The signature attests that the service held the creation data at signing time. A sidecar with a missing artifact still needs access to the service to retrieve it.

<span id="complete-lifecycle" />

## Security Considerations

A matching hash ties the available bytes to the registered ID. Policy behavior requires [testing](./testing-strategy). On Ethereum, the registration event also records when the assignment takes effect. Builder enforcement depends on the active assignment and the [deployment mode](./deploy-assertions-dapp).
