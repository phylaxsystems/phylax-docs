[Assertion Data Availability (Assertion DA)](/credible/glossary#assertion-da-data-availability) is the storage layer that maintains [assertion bytecode](/credible/glossary#assertion-bytecode) and source code, making it accessible to [Assertion Enforcers](/credible/glossary#assertion-enforcer) and providing transparency for users and auditors.

## Purpose

Assertion DA serves two primary functions:

1. **Persistent Storage**: Maintains EVM bytecode of assertions in an accessible location
2. **Integrity Verification**: Validates that on-chain assertion IDs match the Keccak256 hash of the actual assertion bytecode

## Assertion ID

The assertion ID is deterministically derived from the assertion bytecode:

```
Assertion ID = Keccak256(Assertion_EVM_Bytecode)
```

This ensures:
- Each unique assertion has a unique identifier
- Assertion integrity can be verified by recomputing the hash
- Invalid bytecode will fail execution deterministically, so no validation is needed at submission time

## Current Implementation

The current implementation uses a centralized server operated by Phylax Systems:

- **Storage**: Off-chain server stores assertion bytecode and source code
- **Access**: Publicly accessible for transparency and verification
- **Integration**: Works with [`pcl`](/credible/glossary#pcl-cli) and the [Credible dApp](/credible/glossary#credible-dapp). See the [Architecture Overview](/credible/architecture-overview) for details.

<Note>
The Assertion DA is currently centralized. Decentralization is planned for future releases.
</Note>

## How It Works

### Storing Assertions

When you store an assertion using the [`pcl`](/credible/glossary#pcl-cli):

```bash
pcl store MyAssertion
```

`pcl` does the following:
1. Compiles your assertion contract to EVM bytecode
2. Uploads both bytecode and source code to Assertion DA
3. Returns the assertion ID (Keccak256 hash of the bytecode)

Only the contract owner (the address returned by the contract's `owner()` function) can register, modify, or deactivate assertions for their contract. This is enforced on-chain by the Credible Layer smart contracts, which verify ownership before allowing any assertion management operations. During the early phase of the project, there is also a manual whitelist in place. Ownership verification will be expanded and improved in future versions to support additional ownership patterns and multisig integration. See [Ownership Verification](/credible/ownership-verification) for details.

### Retrieving Assertions

Assertion Enforcers fetch assertions from the Assertion DA during transaction validation:

1. **Identify Relevant Assertions**: The system identifies which assertions apply to contracts in the transaction by querying the on-chain [Credible Layer Protocol](/credible/architecture-overview#credible-layer-protocol) registry
2. **Fetch Bytecode**: Assertion Enforcers query Assertion DA using the assertion ID
3. **Verify Integrity**: Verify that `Keccak256(bytecode) == AssertionID`
4. **Cache for Validation**: Store assertion bytecode locally for transaction validation

See the [Architecture Overview](/credible/architecture-overview#assertion-validation-process) for details on how assertions are executed during validation.

## Complete Lifecycle

The complete flow from assertion development to enforcement involves multiple steps:

1. **Development**: Write and test assertions locally using `pcl`
2. **Storage**: Store assertion bytecode in Assertion DA using `pcl store`, which returns the assertion ID
3. **Registration**: Submit the assertion ID to the [Credible dApp](/credible/glossary#credible-dapp), which registers it in the on-chain Credible Layer smart contracts
4. **Linking**: Link the assertion to specific contract addresses that should be protected
5. **Enforcement**: Assertion Enforcers fetch assertions from Assertion DA and execute them during block production

For a detailed view of how these components interact, see the [System Architecture](/credible/architecture-overview#system-architecture) section in the Architecture Overview.

## Design Rationale

### Why Off-Chain Storage?

- **Cost Efficiency**: EVM bytecode can be large; on-chain storage would be prohibitively expensive
- **Performance**: Faster retrieval and caching for high-frequency validation
- **Flexibility**: Enables future improvements without base layer changes

### Why No On-Chain Bytecode Validation?

The protocol intentionally omits bytecode validation because:
- [PhEVM](/credible/glossary#phevm-phylax-evm) execution is deterministic
- Invalid bytecode will consistently fail execution
- This allows Assertion Enforcers to safely discard invalid assertions without verification overhead

## Security Considerations

**Availability**: Critical for system liveness. If Assertion DA fails, Assertion Enforcers cannot validate transactions.

**Integrity**: The Keccak256 hash verification ensures assertions haven't been modified. Each assertion ID uniquely corresponds to its bytecode.

**Transparency**: All assertions are publicly accessible, enabling users and auditors to verify security measures.

**Incentive Alignment**: Invalid assertions only harm the developer who submitted them, as they will fail execution deterministically.

## Technical Requirements

### For Assertion Enforcers

- Must maintain connection to Assertion DA
- Must implement caching layer for active assertions
- Must verify `Keccak256(bytecode) == AssertionID`
- Must handle DA unavailability gracefully

### For Developers

- Use `pcl store` to upload assertions to Assertion DA
- Assertion ID is automatically computed and returned
- Source code is stored alongside bytecode for transparency
- Assertion ID is used to submit assertions to the [Credible dApp](/credible/glossary#credible-dapp)
