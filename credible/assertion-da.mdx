---
title: 'Assertion Data Availability'
description: 'How assertion bytecode is stored and accessed in the Credible Layer'
---

Assertion DA stores assertion bytecode and source code. The platform stores these artifacts when you run [`pcl apply`](./apply-assertions). Enforcers retrieve bytecode for execution. Reviewers can inspect the source.

## Purpose

Assertion DA stores artifacts and binds each assertion ID to its deployable creation data.

## Key Concepts

### Assertion ID

The assertion ID is deterministically derived from deployable creation data:

```text
Assertion ID = Keccak256(Creation_Bytecode ++ Encoded_Constructor_Arguments)
```

The bytecode and encoded constructor arguments are stored separately in Assertion DA and combined to reconstruct the deployment data.

Recompute the hash to check artifact integrity. Assertion DA compiles submitted Solidity source in a Dockerized `solc` environment before storage.

### Assertion DA Prover Signature

Assertion DA signs an availability proof when it stores an assertion. Deployment uses this proof to check artifact availability.

## Current Implementation

Phylax operates the offchain storage service. Assertion artifacts are publicly accessible for review and verification.

## How It Works

### Storing Assertions

1. `pcl apply` compiles the assertion contracts.
2. The platform uploads flattened source code and compiler options to Assertion DA.
3. Assertion DA generates the assertion ID and availability signature.

The State Oracle checks registration authority and lifecycle timing. See [Managing Policy Deployments](./managing-policy-deployments).

### Retrieving Assertions

Enforcers index the State Oracle's `AssertionAdded` event. They fetch bytecode by assertion ID and cache it before validation.

Operators must define how missing or unreadable artifacts affect validation.

## Complete Lifecycle

An authorized manager registers the assertion through the State Oracle. After the activation delay, enforcers evaluate it in the selected environment.

Production results affect participating builders. Alerting records violations without excluding live transactions. Removal also takes effect after the configured delay. See [Deployment](./deploy-assertions-dapp).

## Design Rationale

### Why Off-Chain Storage?

Offchain storage avoids the cost of storing bytecode and metadata on Ethereum. Enforcers cache artifacts for validation.

### Why Compilation Happens Off-Chain

The State Oracle uses the deployment-data hash and availability signature. Compilation and artifact storage remain outside the contract.

## Security Considerations

Cached assertions remain available during a DA outage. New registrations, restarts, and missing cache entries can require DA access. An availability signature does not guarantee future uptime.

The assertion ID binds the creation bytecode and constructor arguments. It does not establish policy correctness. Test legitimate activity and recovery before activation.
