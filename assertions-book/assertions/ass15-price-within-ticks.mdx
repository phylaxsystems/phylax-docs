Concentrated-liquidity pools have a valid tick range and a spacing rule for initialized ticks. Those rules apply to different values.

<Warning>
The reviewed upstream example needs correction before production use. The limitation below is present in the linked source; the imported code is preserved for comparison.
</Warning>

## Source limitation

`PriceWithinTicksAssertion` checks a current tick against ±887,272 and requires `tick % tickSpacing == 0`. The spacing condition is not valid for a general Uniswap V3 current tick: a pool price can move between initialized ticks. The source also creates a fork identifier without using it for the direct pool read.

## Adaptation requirements

For position boundaries, check that lower and upper ticks are ordered, in range, and divisible by the configured spacing. For the current price, check the protocol's price/tick relationship and chosen price policy without imposing position-boundary alignment. Use the [Uniswap adapters](./protocol-adapters#uniswap) for the matching version.

## Scenarios

| Scenario | Meaning |
| --- | --- |
| Current tick is 1; spacing is 60 | Can be valid in Uniswap V3, but fails the template's spacing condition |
| Position lower tick is 1; spacing is 60 | Invalid position boundary |
| Position bounds are -120 and 120; spacing is 60 | Spacing and ordering pass; valuation is a separate check |

Local PCL tests also show that its direct `slot0()` call can revert before reaching the checks. Use snapshot-aware reads.

Do not deploy this template unchanged as a Uniswap V3 price invariant. A tick within the global range is not proof of a fair price or adequate liquidity.
