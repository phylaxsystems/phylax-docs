title: 'Circuit breakers'
description: 'Overview of cumulative and rate-of-change circuit breakers for ERC20 balance changes'

Circuit breakers limit unusual ERC20 balance changes. They can reject a candidate transaction before it settles.

## What they watch

- **Adopter:** The contract protected by the assertion.
- **Token:** The ERC20 balance being watched.
- **Direction:** Tokens entering or leaving the adopter.
- **Time:** Balance changes across blocks and transactions.

## Use them separately or together

Each circuit breaker can enforce its own limit.

Rate of change can be used as an independent trigger. It can also be combined with a cumulative trigger.

| Risk | Circuit breaker |
| --- | --- |
| Too many tokens leave over time | Cumulative outflow |
| Too many tokens enter over time | Cumulative inflow |
| The balance changes too quickly | Rate of change |
| Total flow and flow speed must both be bounded | Cumulative and rate of change |

When triggers are combined, the assertion can reject a transaction when either limit is exceeded.

## Aave V4 example

Aave checks each supply, borrow, withdrawal, and liquidation. These checks do not track total Hub custody movement across operations and time.

Credible Layer watches the actual ERC20 balances of the Core and Prime Hubs. It does not depend on every token-moving path calling an onchain breaker.

- A missed function or approved transfer cannot bypass the balance check.
- No breaker code or storage is added to Aave.
- User transactions do not pay extra gas for breaker accounting.

Aave combines cumulative and rate limits using the same balance history.

The Aave V4 assertion suite watches these Hub balances:

| Adopter | Watched assets |
| --- | --- |
| Core Hub | WBTC, USDG, and wstETH |
| Prime Hub | WBTC and wstETH |

Each Hub adopts a circuit breaker. For each watched asset, the policy checks:

- Cumulative inflow over a rolling 24-hour window.
- Cumulative outflow over a rolling 24-hour window.
- Peak inflow rate.
- Peak outflow rate.

The transaction is rejected when any configured limit is exceeded.

The limits cover different flow patterns:

| Flow pattern | Limit that can stop it |
| --- | --- |
| Fast movement in one block | Peak rate |
| Smaller movements across many blocks | Cumulative flow |
| Either limit is exceeded | Transaction rejected |
