A treasury policy may limit the native ETH lost in one transaction. The legacy `EtherDrainAssertion` intends to cap that loss at 10% of the starting balance.

<Warning>
The reviewed upstream example needs correction before production use. The limitation below is present in the linked source; the imported code is preserved for comparison.
</Warning>

## Source limitation

The current source creates `_preTx()` and `_postTx()` identifiers but reads `address(adopter).balance` directly both times. Creating the identifiers does not switch state. The code therefore does not implement the intended before-and-after balance comparison. It also contains no destination allowlist. A local PCL test withdrew 90 ETH from a 100 ETH fixture without triggering the intended cap.

## Adaptation requirements

Do not activate this example as an ETH drain limit. A replacement needs a supported native-balance observation at explicit snapshots, or a verified protocol getter read with `ph.staticcallAt`. The chosen getter must return actual custody rather than a mutable accounting counter. Native ETH is not an ERC-20: configuring a cumulative ERC-20 watcher with `address(0)` is not a substitute.

## Scenarios

| Scenario | Meaning |
| --- | --- |
| 100 ETH becomes 91 ETH | Would pass the intended 10% net-loss policy |
| 100 ETH becomes 89 ETH | Should fail; the current example does not establish that check |
| 20 ETH leaves and 20 ETH returns in the same transaction | Net-loss policy sees zero loss |
| Repeated transactions each withdraw 9% | A per-transaction policy does not impose a rolling cap |

The table defines acceptance tests for a corrected adapter. It is not a claim that this source enforces them. Test withdrawals, forced receipts, value-bearing nested calls, and rollback. Wrapped ETH held as ERC-20 can use the [ERC-20 outflow breaker](./ass20-erc20-drain), but that covers only the wrapped balance.
