An attacker can change a price, borrow against it, then restore it in one transaction. Equal transaction endpoints do not show the price used by the borrow.

<Warning>
The reviewed upstream example needs correction before production use. The limitation below is present in the linked source; the imported code is preserved for comparison.
</Warning>

## Source limitation

The legacy `IntraTxOracleDeviationAssertion` intends to compare each update with a 10% band around the starting price. It constructs transaction and call fork identifiers but does not pass them into its `price()` reads. Repeated direct reads do not inspect the named snapshots. In the local PCL test, the direct getter call reverted before the deviation comparison, including for an update inside the intended band.

## Adaptation requirements

For a writable oracle, bind each observed update to its call ID and read at that call's boundary. For a lending operation, inspect the oracle result actually consumed by that operation. A consumed value can differ from both stored endpoints. The [Aave adapters](./protocol-adapters#aave) illustrate version-specific consumed-price checks.

## Scenarios

| Scenario | Meaning |
| --- | --- |
| Price starts at 100 and a covered update sets 105 | Within an intended 10% band |
| Price becomes 150, is used for borrowing, then returns to 100 | Must be tested at the consumption boundary |
| An external oracle changes without calling the protected contract | Adopter-trigger coverage must be established separately |

Do not rely on the source below to catch a temporary price excursion. Test multiple updates, reverted calls, nested reads, oracle replacement, and restoration in a single transaction. Match the baseline and observation point to the actual lending decision.
