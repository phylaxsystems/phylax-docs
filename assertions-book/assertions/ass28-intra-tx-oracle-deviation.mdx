---
title: "In-Transaction Oracle Changes"
description: "Compare covered oracle updates with explicit call snapshots"
---

A price can leave its allowed range and return before transaction end. Comparing only transaction endpoints misses that excursion.

## Policy and scope

**Spec:** Reshiram. **Evidence:** locally tested synthetic oracle. **Lifecycle:** adaptation example, not a KiloEx replay or a production oracle policy.

`OracleSnapshotsAssertion` below compares slot zero after every covered `updatePrice(uint256)` call with its pre-transaction value. It permits an absolute difference of at most `start / 10`, using integer rounding. A zero starting price therefore permits only zero. The 10% band illustrates behavior; it is not a recommended market threshold.

## Scenarios

| Starting price | Covered updates | Expected result |
| --- | --- | --- |
| 100 | 90 through 110 | Allowed |
| 100 | 89 or 111 | Rejected |
| 100 | 150, then 100 | Rejected despite restoration |
| 100 | 105, then 100 | Allowed |
| 0 | 1 | Rejected |

## Adaptation requirements

The fixture has one price slot and one update path. A real lending policy must inspect the value consumed by the borrow or liquidation, including external oracle calls, scaling, freshness, replacement, and reverted calls. An external update that never touches the adopter requires separate trigger coverage. See [Call Frame Context](/credible/use-case-mappings/call-frame-context).
