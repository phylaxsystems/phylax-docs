Several withdrawals, each small enough to look routine, can remove a large share of custody. A cumulative outflow breaker rejects the candidate transaction that takes net outflow above the rolling limit.

## Configuration

`ERC20CumulativeOutflowBreakerAssertion` takes three constructor arguments:

| Argument | Example | Meaning |
| --- | --- | --- |
| `monitoredToken_` | Your underlying ERC-20 address | Token whose balance at the adopter is measured |
| `outflowThresholdBps_` | `1000` | 10% of the window's balance baseline |
| `outflowWindowDuration_` | `86400` | Rolling window in seconds: one day |

Attach the assertion to the contract that holds the watched tokens. The adopter is set by deployment; it is not a constructor argument in this template. Use separate registrations for different tokens or custody addresses.

The template does not validate constructor inputs. Add checks for the token and policy bounds. The window must be at least 10 seconds and fit in `uint64`. For an outflow cap, a threshold of 10,000 bps cannot reject a drain that only reaches 100%; the [Balancer example](./balancer-outflow) rejects that configuration.

## Behavior

`watchCumulativeOutflow` maintains the rolling history in the executor. It invokes `assertCumulativeOutflow` only when net outflow is **strictly greater** than the threshold. The callback checks the token context and reverts. A revert rejects the candidate transaction; it does not write a persistent pause flag to your protocol.

Opposite-direction transfers offset the watched direction. The denominator is the window's `tvlSnapshot`, not the current balance or a USD valuation. See [bucket and baseline semantics](./circuit-breakers).

## Scenarios

Assume a 100,000-token baseline, a 10% limit, and all listed transfers within the retained window. Each row starts from that same baseline with no other flow.

| Transfers | Net outflow | Result |
| --- | ---: | --- |
| 9,999 tokens outflow | 9,999 | No breach |
| 10,000 tokens outflow | 10,000 | No breach: equality is allowed |
| 5,000, then 5,001 tokens outflow | 10,001 | Second transaction triggers rejection |
| 15,000 outflow and 5,000 inflow | 10,000 | No breach after netting |

## Test and adapt

Local `pcl test` does not simulate rolling cumulative dispatch. Constructor tests and an armed callback test can verify configuration and rejection behavior, but they do not prove the table's window behavior. Use an executor-backed environment to test accumulated transactions, equality, expiration, offsetting flow, and zero starting balance.

Check deposits, repayments, strategy transfers, and emergency withdrawals against the intended custody boundary. Token rebases, external strategy custody, and native ETH need their own accounting model. A net flow limit is not a gross-transfer or maximum-loss guarantee.
