## What Happened

Compound Proposal 65 documents over-accrued COMP introduced by Proposal 62 and the corrective work following Proposal 64. The repair distinguishes unclaimed excess accrual from rewards already claimed. This page does not equate an exposed balance, an accrual error, and realized loss. [Compound Proposal 65](https://hackmd.io/@TylerEther/BkdJGdRVY).

## Attack Mechanism

The upgrade changed reward-index initialization. A supplier with an unset index could encounter a market supply index equal to `compInitialIndex` (`1e36`). The affected condition used `supplyIndex > compInitialIndex`, so equality skipped initialization and left the supplier index at zero.

```solidity
// Affected initialization condition; this is protocol code, not an assertion.
if (supplierIndex == 0 && supplyIndex > compInitialIndex) {
    supplierIndex = compInitialIndex;
}
```

The later accrual calculation then used an index difference of roughly `1e36`, rather than the small difference since the supplier's real starting point. The correction had to account for both excess accrual still recorded in storage and rewards already claimed.

`distributeSupplierComp` is an internal Solidity function, so EVM call-input tracing cannot discover those invocations. The example below limits net COMP leaving a configured rewards treasury in one transaction. It contains the payout even when the faulty internal function has already over-accrued rewards.

## Assertion Example

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.29;

import {Assertion} from "credible-std/Assertion.sol";
import {AssertionSpec} from "credible-std/SpecRecorder.sol";
import {PhEvm} from "credible-std/PhEvm.sol";

/// @notice Cap net COMP paid from a configured rewards treasury in one transaction.
contract RewardPayoutLimit is Assertion {
    address public immutable comp;
    uint256 public immutable maximum;
    constructor(address comp_, uint256 maximum_) {
        registerAssertionSpec(AssertionSpec.Reshiram);
        require(comp_ != address(0), "Invalid COMP"); comp = comp_; maximum = maximum_;
    }
    function triggers() external view override { registerTxEndTrigger(this.check.selector); }
    function check() external view {
        bytes memory query = abi.encodeWithSignature("balanceOf(address)", ph.getAssertionAdopter());
        uint256 beforeBalance = abi.decode(read(comp, query, _preTx()), (uint256));
        uint256 afterBalance = abi.decode(read(comp, query, _postTx()), (uint256));
        if (beforeBalance > afterBalance) require(beforeBalance - afterBalance <= maximum, "Reward payout above cap");
    }

    function read(address target, bytes memory data, PhEvm.ForkId memory fork)
        internal view returns (bytes memory)
    {
        PhEvm.StaticCallResult memory result = ph.staticcallAt(target, data, 500_000, fork);
        require(result.ok, "Snapshot read failed");
        return result.data;
    }
}
```

## What This Check Covers

The cap is a policy parameter in COMP base units, not a reconstructed reward schedule. It can reject large legitimate claims and does not fix excess `compAccrued`. Incoming COMP in the same transaction can offset outgoing COMP, so this net-balance cap is weaker than a gross-transfer or cumulative-window policy. Attach it to the paying treasury and test its actual payout paths.
